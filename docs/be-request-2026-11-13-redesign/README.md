## 공통 원칙

1. **계약 우선.** `api.yaml`이 기준이다. 응답에 필드를 **더하는** 것은 v1에 그대로 넣는다.
   기존 필드의 뜻이나 오류 코드가 바뀌면 v2 경로로 분리한다(BE `CLAUDE.md`의 v1/v2 규칙).
2. **사용자 시간대.** "오늘", "이번 주", "지난 마감", "하루 마무리 시각"은 모두
   `users.timezone` 기준이다(`today_in_tz`, `now_in_tz`). 주의 경계는 새 설정 `week_start`를 따른다.
3. **AI는 제안만 한다.** 사용자가 누르기 전에는 데이터를 바꾸지 않는다. 적용한 것은 되돌릴 수 있어야 한다.
4. **지우기는 휴지통으로.** 6단계 이후 할 일과 회고의 삭제는 `deleted_at`을 채우는 것으로 바꾸고, 30일 뒤 영구 삭제한다.
5. **모듈 규칙.** 새 모듈은 `domain → application → infrastructure → presentation` 구조와
   모듈별 Dishka Provider, `main.py` 라우터 등록, Alembic 마이그레이션 규칙을 따른다.
6. **비용 상한.** Gemini를 부르는 기능(주제 정리, AI)은 기존 `digest_rate_limiter`처럼 사용자별 상한을 둔다.

### 순서를 이렇게 정한 이유

- **0단계를 먼저 하는 이유:** 개발자 계정 구분이 남아 있으면 FE가 GitHub 연결 기준으로 바꾼 화면에서 일반 사용자의 커밋 자료가 막힌다. 바꾸는 범위가 작고 다른 단계의 전제다.
- **1단계가 작은 이유:** 묶음 수정과 조회 두 가지뿐인데, FE 3~4단계(오른쪽 패널, 하루 닫기)가 바로 쓴다. 묶음 수정은 5b의 "제안 적용" 트랜잭션을 그대로 재사용한다.
- **2단계를 설정보다 앞에 두는 이유:** 회고 주제 화면은 시안이 끝까지 확정됐고, 구조화 정리가 없으면 화면 전체가 동작하지 않는다. 프롬프트 버전이 바뀌면 기존 정리가 다시 생성되므로, 비용과 시간을 보려면 일찍 하는 편이 낫다.
- **AI를 5a/5b/5c로 나눈 이유:** 추천은 규칙만으로 만들 수 있어 LLM 비용 없이 먼저 낼 수 있다. 대화는 도구 호출과 스트리밍 검증이 필요해 가장 크다.
- **휴지통을 마지막에 두는 이유:** 모든 조회에 `deleted_at IS NULL` 조건이 들어가 영향 범위가 가장 넓다. 다른 단계가 끝난 뒤 한 번에 바꾸고 회귀 테스트를 돌리는 편이 안전하다. 단, AI 되돌리기는 휴지통 없이 변경 전 값으로 되돌리므로 서로 막지 않는다.
