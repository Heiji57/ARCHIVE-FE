# 11. ai (새 모듈): 추천, 대화와 제안, 설정, 예약, 사용량

단계: §2와 §6은 5a, §3과 §4는 5b, §5는 5c. 1차 출시에 전부 포함한다(결정, 2026-11-16).

## 원칙

1. **AI는 제안만 만든다.** 사용자가 "넣기", "적용"을 누르기 전에는 할 일과 회고를 바꾸지 않는다.
2. **적용한 것은 되돌릴 수 있다.** 적용할 때 변경 전 값을 저장하고, 되돌리기는 그 값을 다시 쓴다.
3. **쓰기는 기존 유스케이스로만.** 할 일 변경은 `02-todo.md` §1의 묶음 수정, 회고는 기존 생성 유스케이스를 부른다.
   AI 모듈이 다른 모듈의 테이블에 직접 쓰지 않는다.
4. **비동기와 SSE.** 생성은 Celery 작업, 진행은 SSE. 기존 요약과 주제 정리 패턴(Redis pub/sub)을 따른다.
5. **비용 상한.** 사용자별 하루 요청 수와 토큰 상한(§6).

## 모듈 구조

새 모듈 `ai/`. LLM 호출은 `ai/infrastructure/llm/`에 두고, 지금 `topic`의 `GeminiClient`를 공용(`shared/infrastructure/ai/`)으로
옮겨 두 모듈이 같이 쓰게 하는 것을 계획에서 검토한다. 도구 호출(function calling)과 스트리밍을 지원하는지 확인이 필요하다.

## §1. 화면과 대응

| 화면 | 절 |
|---|---|
| 오른쪽 줄 AI 버튼 → 캘린더 흐린 칸(AI 표시) + 종류별 추천 목록, 넣기와 넘기기 | §2 |
| AI 탭: 가운데 입력, 진행 문장, 결과 캘린더 미리보기와 표(넣음/뺌), 확인 | §3, §4 |
| 하루 닫기의 회고 초안, AI 탭의 회고 초안 | §4 `retro_draft` |
| 설정 AI 비서 시트(빗금이, 연결된 도구, 바꾸기 전 확인, 답하는 방식, 알려 둔 것, 예약한 일, 대화 기록) | §5 |

## §2. 추천 (5a, LLM 없이 시작)

### 종류

| 종류 | 규칙 | 행동(최대 2개) |
|---|---|---|
| `overdue` | 마감이 지난 할 일(02 §2와 같은 조건) | "오늘로", "내일로" |
| `free_slot` | 시간 없는 오늘 할 일 + 오늘 일하는 시간(03) 안의 빈 칸 | "오후 5시~6시에 넣기" |
| `unscheduled_long` | 길이를 아는 할 일이 빈 칸보다 김 | "나눠서 넣기"(2차) |
| `commit_match` | 오늘 커밋 메시지와 제목이 겹치는 끝내지 않은 할 일 | "끝냄으로" |

- 1차는 **규칙만**으로 만든다. 이유 문장도 템플릿으로 만든다("10/30 마감이 지났어요").
  LLM으로 이유 문장을 다듬는 것은 2차.
- 빈 칸 계산: 일하는 시간 − 시간이 있는 할 일 − Google 일정(`/calendar/events`와 같은 출처). 기본 길이는 `defaultTodoMinutes`.

### API

- `GET /ai/suggestions?date=YYYY-MM-DD` → `[{ id, kind, todoId, title, reason, slot?: { start, end }, actions: [{ label, patch }] }]`
  - 캘린더 흐린 칸은 `slot`이 있는 추천으로 그린다.
- `POST /ai/suggestions/{id}/apply { actionIndex }` → 묶음 수정 결과와 `undoToken`
- `POST /ai/suggestions/{id}/dismiss` → 같은 추천(같은 종류 + 같은 할 일 + 같은 날)은 다시 나오지 않음
- `POST /ai/suggestions/{id}/undo`

### 저장소

`ai_suggestions(id, user_id, date_key, kind, todo_id, payload JSONB, status: shown|applied|dismissed, previous JSONB, created_at)`.
추천은 요청 때 계산해 저장하고, 같은 날 다시 부르면 상태를 이어 쓴다.

## §3. 대화 (5b)

- `POST /ai/conversations`, `GET /ai/conversations`, `DELETE /ai/conversations/{id}`
- `GET /ai/conversations/{id}/messages`
- `POST /ai/conversations/{id}/messages { text, context? }` → 202, 작업 `worker.run_ai_turn`
- `GET /ai/conversations/{id}/stream`(SSE) 이벤트
  - `step`: 진행 문장("내일 일정을 확인하고 있어요")
  - `delta`: 답변 글자
  - `proposal`: 제안 하나(§4)
  - `done`, `error`

### 도구

모델이 부를 수 있는 도구. **읽기는 바로, 쓰기는 제안으로만.**

| 도구 | 읽기/제안 | 내용 |
|---|---|---|
| `list_todos(from, to)` | 읽기 | 할 일(지운 것 제외) |
| `list_events(from, to)` | 읽기 | Google 일정 |
| `list_commits(from, to)` | 읽기 | 07 §2 |
| `search_retros(q)` | 읽기 | 09 |
| `get_settings()` | 읽기 | 일하는 시간, 주 시작, 기본 길이 |
| `propose_todos(items)` | 제안 | 새 할 일 |
| `propose_moves(items)` | 제안 | 날짜, 시간 바꾸기 |
| `propose_retro_draft(date, text)` | 제안 | 회고 초안 |

설정의 "연결된 도구"(L1)에서 끈 출처(캘린더, 할 일, 회고, GitHub)의 도구는 넘기지 않는다.

## §4. 제안과 적용 (5b)

```json
{ "id": "p1", "kind": "add|move|update|retro_draft", "summary": "할 일 3개를 넣을게요",
  "items": [{ "key": "i1", "todoId": null, "title": "스프린트 회의", "before": null,
              "after": { "dateKey": "2026-11-04", "startTime": "...", "endTime": "..." }, "clash": ["<todo id>"] }],
  "status": "pending|applied|dismissed|undone" }
```

- `POST /ai/proposals/{id}/apply { itemKeys? }` → 고른 항목만(시안의 "넣음/뺌"). 할 일은 묶음 수정과 같은 트랜잭션,
  회고 초안은 회고 생성. 응답에 만들어진 id들.
- `POST /ai/proposals/{id}/undo` → 적용한 것만 되돌림(만든 할 일은 지움, 바꾼 할 일은 `previous`로).
  적용 뒤 사용자가 그 할 일을 또 고쳤으면 그 항목은 되돌리지 않고 `skipped`로 알려 준다.
- `POST /ai/proposals/{id}/dismiss`
- `clash`: 같은 시간에 이미 있는 할 일. 서버가 계산한다.
- 설정 "바꾸기 전 확인"(L5)이 `always`가 아니어도, 1차는 **항상 확인**으로 둔다(자동 적용은 2차).

### 저장소

`ai_conversations(id, user_id, title, created_at, updated_at)`,
`ai_messages(id, conversation_id, role, content, tool_calls JSONB, created_at)`,
`ai_proposals(id, user_id, conversation_id, kind, payload JSONB, status, applied JSONB, previous JSONB, created_at, applied_at)`

## §5. 설정, 기억, 예약 (5c)

### `GET`, `PUT /ai/settings`

| 필드 | 화면 | 값 |
|---|---|---|
| `petEnabled` | L0 빗금이 | bool |
| `tools` | L1 연결된 도구 | `{ calendar, todo, retro, github: bool }` |
| `confirmMode` | L5 바꾸기 전 확인 | `always`(1차 고정) |
| `answerLength` | L2 답하는 방식 | `short` \| `normal` \| `detail` |
| `deepSearch` | L2 | bool |
| `memoryEnabled` | L3 | bool |
| `retentionDays` | L6 대화 기록 | 30 \| 90 \| 365 \| 0(보관 안 함) |

### 기억(알려 둔 것)

- `GET /ai/memories`, `POST /ai/memories { text }`, `DELETE /ai/memories/{id}`. 최대 50개, 200자.
- 대화마다 프롬프트 앞에 싣는다. 모델이 스스로 기억을 만들지는 않는다(1차).

### 예약한 일

- `GET`, `POST /ai/schedules`, `PATCH`, `DELETE /ai/schedules/{id}`
- 본문: `{ prompt, repeat: { unit: "day" | "week", weekdays?: number[], at: "HH:mm" }, enabled }`. 시각은 사용자 시간대 기준.
- 작업 `worker.dispatch_ai_schedules`(5분마다)가 시각이 된 예약을 대화로 실행하고, 결과를 `category: schedule` 알림으로 보낸다.
  만들어진 제안은 알림 링크로 연다(적용은 사용자가).

### 대화 기록 정리

작업 `worker.purge_ai_conversations`(하루 한 번)가 `retentionDays`보다 오래된 대화와 적용 안 한 제안을 지운다.

## §6. 사용량 (5a부터)

- `GET /ai/usage` → `{ day: { used, limit }, month: { used, limit } }`. 기존 `/summaries/usage`와 같은 모양.
- 상한을 넘으면 `AI_QUOTA_EXCEEDED`(429). 추천(규칙 기반)은 상한에 세지 않는다.
- 토큰 사용량을 `ai_usage(user_id, date_key, requests, input_tokens, output_tokens)`에 쌓는다.

## 오류 코드

`AI_QUOTA_EXCEEDED`(429), `AI_PROPOSAL_NOT_FOUND`(404), `AI_PROPOSAL_ALREADY_APPLIED`(409), `AI_PROPOSAL_STALE`(409, 적용 전에 대상 할 일이 바뀜),
`AI_SUGGESTION_NOT_FOUND`(404), `AI_TOOL_DISABLED`(400), `AI_LLM_UNAVAILABLE`(503)

## 확인할 것

- Gemini 클라이언트로 도구 호출과 스트리밍이 되는지, 안 되면 어떤 SDK 기능을 쓸지
- 대화 한 번의 토큰 상한과 하루 상한 숫자
- 개인정보: 회고 원문을 모델에 보낼 때의 고지(설정 화면 문구는 FE)

## 테스트

- 추천: 마감 지남, 빈 칸 계산(일하는 시간 밖 제외, Google 일정 겹침), 숨긴 추천 재등장 없음
- 제안 적용: 일부 항목만, 트랜잭션 롤백, 되돌리기 후 상태, 적용 뒤 사용자가 고친 항목 `skipped`
- 도구: 끈 출처의 도구가 호출되지 않음
- 사용량 상한과 429
